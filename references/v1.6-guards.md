# Ghost Busters v1.6 — Runtime Identity, Human Alert, Regression Evidence

v1.6 adds three **offline, deterministic evidence gates** to the original four.
They evaluate operator-prepared synthetic or sanitized aggregate summaries.
They do not collect evidence, authenticate sources, access production, execute SQL,
send notifications, execute tests, merge code, or deploy changes.

**Safety:** keep customer project refs, deployment IDs, URLs, phone numbers,
credentials, raw alerts, user names and real CI artifacts in a **private**
evidence ledger. Local JSON contains only minimum technical signals.
Gate outputs deliberately omit refs, artifact IDs and evidence IDs.
Positive status is never authorization for production writes.

## Runtime Identity — three independent channels

The original Environment gate compares operator-supplied refs and an anchor.
The new runtime-identity gate requires THREE different evidence channels:
deployment provider, running application, and read-only database. It checks
project identity, deployed artifact agreement and freshness.

Required fields:
- evaluatedAt: ISO timestamp with UTC offset;
- expectedProjectRef, accessReadOnly (must be true), optional maxAgeMinutes
  (default 60; bounded 1–10080);
- deployment: source="deployment-provider", projectRef, artifactId,
  observedAt, evidenceId;
- runtime: source="runtime-response", projectRef, artifactId,
  observedAt, evidenceId;
- database: source="readonly-database", projectRef, observedAt, evidenceId,
  anchorRows, minimumRows.

Each evidenceId must point to a *distinct private observation*. The gate
does NOT retrieve or authenticate it. The runtime binding must come from
an authenticated observation of the deployed application, not from
README/source code copied a second time. Do not publish an unauthenticated
health endpoint or disclose a database project ref just to pass this gate.
Use existing trusted deployment/runtime telemetry.

Statuses: CORROBORATED_CANDIDATE, MISMATCH, STALE_EVIDENCE, UNSAFE_ACCESS,
INSUFFICIENT_EVIDENCE. Even CORROBORATED_CANDIDATE is only corroborated
operator assertions; independently verify private originals before claiming
the live system identity.

## Human Alert — detection is not acknowledgement

A watchdog can run successfully and create a task nobody ever receives.
The human-alert gate checks creation, external delivery and real human ACK.

Required fields:
- evaluatedAt, detectedAt, and nullable createdAt, deliveredAt,
  acknowledgedAt (offset-qualified ISO timestamps).
- incidentChannel and alertChannel (generic type like "whatsapp" or "email"),
  channelIndependent (boolean, false if outage breaks alert channel too).
- Optional maxCreateMinutes (default 15), maxDeliveryMinutes (10),
  maxAckMinutes (30), all bounded 1–10080.
- deliveryEvidenceId and ackEvidenceId when those events occurred,
  stored as references to private provider and human records.

Statuses: DEPENDENT_CHANNEL, ALERT_MISSING, ALERT_PENDING,
DELIVERY_OVERDUE, DELIVERY_PENDING, DELIVERY_UNVERIFIED, ACK_OVERDUE,
ACK_PENDING, ACK_UNVERIFIED, ACKNOWLEDGED.

ACKNOWLEDGED requires independent channel, correct chronology and recorded
delivery and human-acknowledgement evidence. A task marked "open" is not
conclusive evidence that nobody received a separate alert; conversely a
stored task is never proof of delivery.

The Hunter produces a *local report only*. It does NOT send a message,
page an on-call person or acknowledge an incident. Real paging needs a
separate approved private integration.

## Regression — real RED before claimed GREEN

Regression gate validates the **operator-supplied CI/fixture outcome summary**
for one unchanged test case. It does not run the test.

Required:
- evaluatedAt, testId, fixRevision, environment="isolated".
- before: outcome="FAIL", observedAt, evidenceId.
- after: outcome="PASS", observedAt later than before, distinct evidenceId.
- negativeControls: total > 0 and passed equal to total.
- Optional independentReview: completed, evidenceId, reviewedAt (attestation,
  not an authenticated independent verification).

Statuses: RED_GREEN_RECORDED, INSUFFICIENT_EVIDENCE, NO_RED_BASELINE,
POST_FIX_FAILURE, CONTROL_FAILURE, UNSAFE_TEST_ENVIRONMENT.
Never write to production for a diagnostic regression test.
Even RED_GREEN_RECORDED requires an independent check of original test
outputs and the actual released artifact before a FIXED claim.

## CLI: offline usage

Requires Node.js 20+. All example JSON documents are synthetic.

~~~bash
node references/ghost-guard.cjs runtime-identity --input examples/runtime-corroborated.json --json --strict
node references/ghost-guard.cjs human-alert --input examples/human-alert-overdue.json --json
node references/ghost-guard.cjs regression --input examples/regression-recorded.json --json --strict
npm test
~~~

Strict exit codes: 0 = the relevant positive assertion is recorded,
1 = incomplete or unsafe evidence, 2 = invalid input. A normal non-strict
command exits 0 after a syntactically valid assessment, even if status
is unsafe. The output never includes raw input, private URLs or tokens.

## Autonomous Hunter integration

All three modes are valid checks in the existing Hunter version-1 config.
Existing configs and alert state are backward-compatible. Like Pulse,
each new evidence summary includes evaluatedAt. The Hunter rejects stale,
future-dated or missing evaluation timestamps; UNKNOWN cannot recover
an active alert.

- GOOD: CORROBORATED_CANDIDATE, ACKNOWLEDGED, RED_GREEN_RECORDED.
- BAD: mismatched/unsafe/stale runtime; missing/overdue/unverified alert;
  missing RED, failing post-fix regression or negative controls; evidence error.
- UNKNOWN: unverified anchor, pending delivery/ack, or incomplete tests.

The Hunter reports only whitelisted booleans and counts. Real collector
endpoints must be deployed and permissioned in a separate PRIVATE repo.
See references/autonomous-hunter.md for safe read-only collection patterns.

## Synthetic incident lesson

A messaging pipeline silently stopped while a scheduler continued reporting
success and an urgent task remained unresolved. That does not establish
the cause of the provider interruption, delivery of the alert, or which
runtime/database was used. Instead obtain real private provider/runtime/DB
and notification receipts, then conduct isolated RED/GREEN tests.

These examples do **not** contain real customer identifiers, alerts,
production metrics or private GitHub issues.
