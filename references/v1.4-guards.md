# Ghost Busters v1.4 — evidence gates

v1.4 converts four parts of the existing investigation protocol into **pure, offline, deterministic checks**. They do not diagnose every production fault and do not replace the 8-phase HUNT.

## First principle: safety and provenance

- Runs against **small, explicitly prepared JSON summaries**; never queries a production database, sends messages, merges PRs, alters permissions, or deploys.
- Prefer aggregate counts, timestamps, SHA-like hashes, booleans and generic names. **Do not supply credentials, customer data, phone numbers, medical information, raw financial transactions, or secret identifiers.**
- Inputs are *assertions supplied by the operator*, not automatically trusted observations. Evidence and timestamps need their own provenance (issue, CI job, DB query, log record).
- A successful static detector or JSON gate is **not** proof that an incident is fully resolved.
- `--strict` exits 0 only for a positive clearance (Pulse: progress observed; Impact: clear; Release: verified in production; Environment: candidate identity verified); 1 means stop/review; 2 means invalid input.

## Run

Requires Node.js 20+:

```bash
node references/ghost-guard.cjs pulse --input examples/pulse-suspected.json --json
node references/ghost-guard.cjs impact --input examples/impact-blocked.json --strict
node references/ghost-guard.cjs release --input examples/release-unverified.json --json
node references/ghost-guard.cjs environment --input examples/environment-mismatch.json --json
npm test
```

Examples are **synthetic**, inspired by incident classes. Neither real customer data nor production Supabase project refs are included.

### Pulse — class 1 / muted watchdog

`pulse` compares *execution success*, *source content freshness*, *downstream progress*, and a *separate activity signal*. To classify a suspected silent failure, the submitted window must have:

1. At least three successful runs with zero imported rows.
2. At least three identical source fingerprints/row counts.
3. Zero new downstream records.
4. Independent upstream/business activity (a count > 0).
5. An explicitly supplied business-hour schedule and at least the configured number of business hours in the observation window (default 2). Weekdays use ISO 1=Monday … 7=Sunday and a real IANA timezone.

Statuses: `SUSPECTED_SILENT_FAILURE`, `NEEDS_INVESTIGATION`, `EXECUTION_FAILURE`, `PROGRESS_OBSERVED`, `INSUFFICIENT_EVIDENCE`.

Important: source activity and downstream records need not match 1:1 (sales, bookings, shipments, etc.); this is **suspicion**, not proof of why the source stalled. Holidays, source schedule, upstream delay and data ownership must be checked. A green cron run is never a freshness check.

Inputs: `evaluatedAt`, `windowStart`, `windowEnd` (offset-qualified ISO dates), `timezone`, `businessHours: {weekdays,from,to}`, `minimumBusinessHours`, `runs: [{at,ok,rowsImported}]`, `snapshots: [{at,fingerprint,rowsCount}]`, `downstream:{newRecords}`, `independentSignal:{activityCount}`. Samples outside the declared window are ignored.

### Impact — class 3 / dangerous widening of a data set

`impact` models what becomes actionable when a fix removes a row cap, permission filter, eligibility gate or stale cache. It blocks release if a newly visible record is unsafe, any dependency is explicitly unmet, or an actionable bulk operation's safeguard fails.

Input fields:

```json
{
  "beforeVisible": 1000, "afterVisible": 1682,
  "hiddenRecordsReviewed": true,
  "unsafeNewRecords": 402,
  "bulkActionsReviewed": true,
  "dependencyReviewComplete": true,
  "bulkActions": [
    {"name":"Send all", "canActOnNewRecords":true, "safeguardsVerified":false}
  ],
  "dependencyChecks":[{"id":"stale-record-validation","passed":false}]
}
```

Statuses: `BLOCKED`, `REVIEW_REQUIRED`, `CLEAR`. An unreviewed expanded population is **never** silently treated as safe. `CLEAR` confirms only the supplied review summary and does not authorize a production change.

### Release — class 5 / code ≠ production

Do not call an error `FIXED` solely because a PR exists, tests are green or a commit was merged. `release` separates:

- `FIX_PREPARED` — fix not merged and in main.
- `MERGED_NOT_DEPLOYED` — not proven in the deployed artifact.
- `DEPLOYED_UNVERIFIED` — deployed, but no valid runtime observation.
- `BLOCKED` — required CI failed, migration not applied, environment mismatch, or test observed before deployment.
- `VERIFIED_IN_PRODUCTION` — all necessary evidence is supplied, including post-deploy smoke verification.

Input:

```json
{
  "prMerged":true,"commitInMain":true,"requiredCiPassed":true,
  "deploymentContainsFix":true,"productionSmokePassed":true,
  "environmentVerified":true,
  "migrations":{"required":false},
  "deployedAt":"2026-10-22T12:00:00Z",
  "smokeObservedAt":"2026-10-22T12:30:00Z"
}
```

No production deploy verification is performed by the tool: the **operator must obtain and attach the evidence**. `deployedAt` / `smokeObservedAt` are recommended; if either is supplied, their order is enforced. Migration requirements are project-specific and require owner approval.

### Environment — identify the actual system

A display name such as “`app-prod`” is insufficient to identify the live database. `environment` compares the configured project ref, connected project ref and deployed application's configured ref, and checks an expected nonempty business-data anchor. It **also requires a read-only operator session** to clear the gate.

Statuses: `VERIFIED_CANDIDATE` (sufficient identity evidence, not write permission), `MISMATCH`, `INSUFFICIENT_EVIDENCE`, `UNSAFE_ACCESS`.

```json
{
  "expectedProjectRef":"redacted-stable-ref",
  "observedProjectRef":"redacted-stable-ref",
  "deployedProjectRef":"redacted-stable-ref",
  "accessReadOnly":true,
  "anchor":{"name":"orders","observedRows":1200,"minimumRows":100}
}
```

Project refs in local reports should be redacted for external publication; validate equality before redaction. A higher count alone does not identify production.

## Evidence-gated investigation

When documenting a real incident, put **four fields in the report**:

```text
ENVIRONMENT  verified candidate / unknown / mismatch; evidence location, role
PULSE        status and source-of-truth timestamps
IMPACT       newly visible rows, downstream actions, dependencies, clearance
RELEASE      PR → main → CI → artifact → migration (if needed) → smoke → status
```

If any field is not applicable, write `N/A` and why. A `PULSE` warning is not a license to fix an external source without proof of ownership. A blocked `IMPACT` or `RELEASE` must not be bypassed simply because tests passed.

## Controlled evaluation

Run `npm test` for existing scanners and the v1.4 guards. Small hand-written tests prove regression behavior for specific fixtures; they are **not** a blind production accuracy measure or head-to-head scores against third-party skills.
